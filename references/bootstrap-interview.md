# Bootstrap interview

Run this before `bootstrap_atlas.py` (existing or greenfield). Ask each question as its own
message and wait for the answer before asking the next.

## 1. Public-facing site URL

Ask for the public-facing site URL so tests can later be generated and run against it. Pass it as
`--site-url`; it lands in `agent-playbook.md`. Greenfield projects may already have a staging URL.
If none exists yet, pass an empty string.

## 2. Design reference

Ask: "Is there a design system or set of design docs/mockups to reference when building new
pages? If so, what folder should I look in?" Ask even when the scan detected nothing; this is a
question for the user, not a scan.

- No / none → skip. No `design-rules.md` is written unless step 3 produces one.
- A folder is named → confirm it exists, read its contents (mockups, style guides, exported
  screens, design tokens, component libraries, brand guidelines — whatever is actually there),
  and write `project-atlas/design-rules.md` summarizing color palette, typography,
  spacing/layout conventions, component patterns, and explicitly stated guidelines. Back each
  point with a repository-relative evidence path. Put anything inferred rather than stated under
  an "Open questions" section.

## 3. Live-site scan (only when step 1 produced a URL)

Ask whether to scan the live site to learn how it is designed. This is opt-in: a URL being present
only means it is worth asking.

If the user opts in, fetch a small representative sample of pages (home plus a couple of interior
pages) and add a `## Live site` section to `design-rules.md`: observed color palette, typography,
layout/component patterns, and navigation conventions. Cite the page URL as each point's evidence
and put anything uncertain under "Open questions". This runs whether or not a design folder was
named; with neither a folder nor a scan, no `design-rules.md` is written.

`design-rules.md` is hand-authored prose, never regenerated by maintenance. If the design folder
changes later, refresh it by hand or rerun steps 2–3.

## 4. Database

Confirm the presence and engine of a database with the user before `database.md`/`schema.md`
stubs are created; detected evidence is a hypothesis, not a fact. If the user opts into live
connection setup, follow `database-connection-setup.md` exactly (one question at a time, no silent
skip). If the user declines, record the explicit skip in `database.md` and continue without a
connection. Both stubs hold names and conventions only, never connection values.
